00

Resumen ejecutivo

Este plan incorpora el spec completo que definiste: Finmate pasa de agente conversacional básico a un asistente financiero proactivo, personalizable y con memoria persistente, con cuatro funciones (noticias/datos económicos, portafolio, mercados, finanzas personales), personalidad configurable, y un Centro de Control web para administrar todo sin tocar código.

Lo más importante que cambia respecto del plan anterior: el agente ya no solo responde — debe iniciar conversaciones dentro de horarios configurados por el usuario. Eso trae dos piezas nuevas que antes no eran necesarias: un scheduler proactivo consciente de horarios/timezone por usuario, y resolver una restricción real de WhatsApp Business sobre mensajes iniciados por el negocio (ver sección 3). También aparece la necesidad de un sitio web propio (Centro de Control), que hoy no existe en el proyecto.

Para cada decisión técnica se presenta la mejor opción sin considerar el costo, y una alternativa más económica — vas a ver ambas en tarjetas a lo largo de la sección 1, y el roadmap de la sección 4 las referencia por nombre en vez de repetirlas.

01

Decisiones técnicas: mejor opción vs. económica

Once decisiones agrupadas en cuatro áreas. La columna izquierda de cada tarjeta es la mejor opción ignorando el costo; la derecha, la alternativa más razonable si el costo importa.

Grupo A — Inteligencia y memoria
01

Modelo LLM que orquesta al agente

Mejor opción
Claude Opus en todas las tareas de razonamiento
Mayor calidad de análisis financiero, mejor manejo de matices de personalidad y de contexto largo (historial + portafolio + noticias a la vez).
Costo por token más alto — sube con cada mensaje proactivo.
Alternativa económica
Enrutado por complejidad: Haiku por defecto, Sonnet solo para portafolio/económicos
La mayoría de los mensajes (saludos, cotizaciones puntuales) no necesitan el modelo más caro. Se reserva el modelo grande para análisis de portafolio y datos económicos.
Reduce el gasto de forma significativa sin perder calidad donde más importa.
02

Base de datos y memoria estructurada

Mejor opción
Postgres gestionado de alta disponibilidad + Redis para caché/sesión
Backups automáticos, réplicas, cero downtime en mantenimiento, y Redis acelera lecturas frecuentes (cotizaciones, watchlist) sin golpear la base principal.
Dos servicios gestionados en vez de uno.
Alternativa económica
Addon de Postgres de Railway (ya integrado al proyecto)
Un solo proveedor, cero configuración adicional, pago por uso acorde al tamaño real de los datos. Suficiente para uso personal o de pocos usuarios.
Bajo, escala junto con lo que ya pagás en Railway.
03

Memoria semántica (recordar preferencias dichas en lenguaje libre)

Mejor opción
Vector DB dedicada (ej. Pinecone o Weaviate gestionado)
Recall semántico robusto: si el usuario dijo "avisame si algo grande pasa con bancos regionales" hace tres semanas, lo encuentra aunque no use esas palabras exactas después.
Servicio adicional, cobra por volumen de vectores.
Alternativa económica
pgvector como extensión del mismo Postgres
Mismo motor de base de datos que ya tenés, sin infraestructura nueva. A la escala de un usuario o pocos, el rendimiento es más que suficiente.
Gratis — es una extensión, no un servicio aparte.
Grupo B — Datos financieros
04

Cotizaciones (acciones, ETFs, bonos, commodities, cripto, FX)

Mejor opción
Polygon.io (plan premium multi-asset)
Cobertura completa en un solo proveedor incluyendo bonos y opciones, baja latencia, datos de calidad institucional — evita mantener 3-4 integraciones distintas.
Plan pago mensual, escala con volumen de requests.
Alternativa económica
Finnhub + Alpha Vantage + CoinGecko (lo que ya usa el bot, + cripto)
Cubre acciones, ETFs, FX y cripto en tiers gratuitos o casi gratuitos. Faltan bonos con buena cobertura, pero es un hueco menor si no es prioridad para el usuario.
Gratis a bajo volumen — mismas APIs que ya están configuradas en Railway.
05

Calendario económico (consenso + dato anterior)

Mejor opción
Trading Economics API
Estándar de la industria: cobertura global de indicadores, siempre con consenso de mercado y dato anterior — exactamente lo que pide el spec para el pre-aviso.
Plan pago, sin tier gratuito útil para este caso.
Alternativa económica
Calendario curado a mano para ~10-15 indicadores clave (Fed, CPI, NFP, PIB, IPC Chile)
Se arma una tabla propia con fechas conocidas de antemano (los bancos centrales publican calendarios oficiales gratis) y se actualiza el consenso manualmente o vía fuentes gratuitas cuando esté disponible.
Gratis, pero requiere mantenimiento manual y cobertura limitada a lo que el usuario más sigue.
06

Noticias financieras filtradas

Mejor opción
Benzinga News API
Feed profesional con etiquetas por ticker/sector/país y sentiment ya calculado — el filtrado por preferencias del usuario es mucho más preciso que buscar palabras clave a mano.
Plan pago por volumen de requests.
Alternativa económica
Finnhub News (ya integrado) + filtrado por keywords con el LLM
Se usa el feed gratuito que ya trae el bot, y se le pide al LLM que decida qué noticia es relevante para cada usuario según sus preferencias guardadas — menos preciso que un feed etiquetado, pero funcional.
Gratis a bajo volumen.
Grupo C — Entrega proactiva
07

Mensajería proactiva por WhatsApp

Mejor opción
Número de WhatsApp Business aprobado + plantillas pre-aprobadas por Meta
Es la única forma confiable de que el agente "avise proactivamente" sin depender de que el usuario haya escrito en las últimas 24 horas — ver la restricción explicada en la sección 3.
Costo por conversación iniciada por el negocio, más el trámite de aprobación de plantillas.
Alternativa económica
Seguir con el número/sandbox actual, aceptando la limitación
Sirve para desarrollo y para un uso personal donde el propio usuario reactiva la ventana de 24h escribiéndole al bot seguido — no cumple el requisito de proactividad total del spec, pero es gratis y ya está andando.
Gratis, pero es un parche, no una solución del requisito.
08

Motor de tareas proactivas (scheduler)

Mejor opción
Orquestador de workflows durable (Temporal.io o AWS EventBridge Scheduler)
Resiliente a caídas del servidor, reintentos automáticos, y escala sin esfuerzo a muchos usuarios con horarios y timezones distintos.
Infraestructura adicional a operar (o costo gestionado en cloud).
Alternativa económica
APScheduler dentro del mismo proceso Flask (como ya existe en main.py)
Cero infraestructura nueva. Funciona bien para pocos usuarios; el riesgo es perder triggers en memoria si el proceso se reinicia, y no escala bien más allá de un puñado de usuarios.
Gratis — ya está en el proyecto.
Grupo D — Centro de Control
09

Stack del sitio web (Centro de Control)

Mejor opción
Next.js (frontend) + FastAPI (backend dedicado), Vercel + Railway
Mejor experiencia de usuario, tiempos de carga, y separación clara entre el panel y el agente — más fácil de escalar a varios usuarios reales en el futuro.
Dos servicios de hosting en vez de uno, más superficie a mantener.
Alternativa económica
Extender el Flask actual con rutas y formularios (Jinja2)
Un solo servicio corriendo en Railway, sin infraestructura nueva. La interfaz es más simple, pero cubre exactamente los formularios que pide el spec.
Gratis — corre en el mismo servicio que ya está pago.
10

Autenticación del Centro de Control

Mejor opción
Proveedor gestionado (Auth0 o Clerk) con MFA
Seguridad de nivel producción desde el día uno, gestión de sesiones y recuperación de cuenta resueltas sin mantenerlas vos mismo.
Plan pago pasado cierto número de usuarios activos.
Alternativa económica
Flask-Login con contraseña hasheada (bcrypt)
Suficiente para uno o pocos usuarios de confianza. Sin MFA ni login social, pero cero costo y control total del código.
Gratis.
11

Infraestructura general / hosting

Mejor opción
Servicios separados por responsabilidad en cloud gestionado (AWS/GCP) con auto-scaling
Cada pieza (agente, scheduler, DB, Centro de Control) escala de forma independiente y con alta disponibilidad real, multi-región si hiciera falta.
Más complejo de operar y más caro que un solo proveedor.
Alternativa económica
Todo en Railway, como hoy
Un solo proveedor, un solo lugar donde mirar logs y variables de entorno, precio predecible y bajo para el volumen actual de un usuario.
Bajo — es la infraestructura que ya está pagada y funcionando.

03

La restricción de WhatsApp que hay que resolver

Esto no es una decisión de costo, es una regla de la plataforma que condiciona todo el requisito de proactividad.

!

WhatsApp Business solo permite texto libre dentro de una ventana de 24 horas desde el último mensaje del usuario. Un mensaje que el agente inicia por su cuenta — apertura de mercado, dato económico publicado, resumen semanal — fuera de esa ventana debe usar una plantilla pre-aprobada por Meta, no texto libre. Sin esto resuelto (decisión 07), la proactividad automática del spec simplemente no funciona más allá de la ventana de 24h.

Implica dos cosas concretas para el plan: (1) hay que registrar y aprobar plantillas para cada tipo de alerta proactiva antes de la Fase 2, y (2) la aprobación de Meta puede tardar días, así que conviene iniciar ese trámite en paralelo mientras se construyen las fases 0 y 1.

04

Plan paso a paso por fases

Nueve fases, cada una con un entregable probable de punta a punta antes de pasar a la siguiente.

0
Cimientos

Base de datos y orquestador

Objetivo: tener el patrón agente-con-tools funcionando de punta a punta, aunque sea con una sola función.

  • Elegir y provisionar la base de datos (decisión 02) y crear las tablas base: users, conversation_history.
  • Elegir el modelo LLM (decisión 01) y dar de alta la API key en Railway.
  • Reemplazar el router de comandos actual por un orquestador con tool-calling, empezando solo con la tool de mercados (ya probada en producción).
  • Iniciar en paralelo el trámite de plantillas de WhatsApp (sección 3) — tarda días en aprobarse.
1
Memoria y personalidad

Historial + personalidad configurable

Objetivo: el agente recuerda la conversación y habla con un estilo propio, sin tocar aún la calidad del análisis.

  • Guardar y recuperar conversation_history en cada turno.
  • Crear personality_settings e inyectarlo dinámicamente en el system prompt (humor, sarcasmo, frecuencia de chistes, nivel conversador, tono).
  • Reforzar explícitamente en el system prompt que la personalidad nunca baja el rigor del análisis financiero.
  • Centro de Control — versión mínima: solo login + edición de perfil y personalidad (para no depender de editar la base a mano).
2
Función 3

Mercados y cotizaciones con contexto

Objetivo: actualizaciones automáticas en apertura/cierre que explican el "por qué", no solo el número.

  • Resolver mensajería proactiva de WhatsApp (decisión 07) — requisito duro antes de este punto.
  • Implementar el scheduler proactivo (decisión 08) consciente de timezone y horarios por usuario, con watchlist_items.
  • Tool que combina precio + variación + búsqueda de noticia relacionada para explicar el movimiento.
  • Alertas en apertura, cierre y horarios custom, respetando feriados de mercado.
3
Función 2

Portafolio

Objetivo: análisis siempre anclado a las posiciones reales del usuario, nunca genérico.

  • Tools de alta/edición/baja de posiciones vía chat, con portfolio_holdings.
  • Cálculo de valor actual, rentabilidad absoluta y %, P&L por posición y total, distribución/exposición.
  • Cruzar posiciones con noticias relevantes y con riesgos/oportunidades — el LLM recibe el portafolio como contexto obligatorio en cada análisis.
  • Centro de Control: módulo de portafolio (alta/edición visual de posiciones).
4
Función 1

Noticias y datos económicos

Objetivo: pre-aviso y post-publicación de datos económicos, resúmenes personalizados.

  • news_topics_followed y economic_indicators_followed + su edición en el Centro de Control.
  • Integrar calendario económico (decisión 05): pre-aviso con dato, fecha, dato anterior, consenso, relevancia y escenarios.
  • Post-publicación: resultado real, comparación con expectativa, interpretación e impacto en activos relevantes.
  • Resúmenes diarios/semanales personalizados; cada alerta queda abierta a preguntas de seguimiento (ya lo resuelve la memoria conversacional de la Fase 1).
5
Función 4

Finanzas personales y presupuesto

Objetivo: registrar gastos hablando normal, y ver el mes de un vistazo cuando se pregunte.

  • Extracción estructurada de gasto (monto, fecha, descripción, categoría) desde lenguaje natural, guardado en transactions.
  • Set inicial de budget_categories (propuesta: Vivienda, Alimentación, Transporte, Ocio, Salud, Educación, Otros) — ajustable desde el Centro de Control.
  • Resumen mensual automático: total, por categoría, distribución %, principales fuentes, comparación con meses anteriores.
  • Consulta on-demand del gasto acumulado durante el mes en curso.
6
Calidad de la proactividad

Control de ruido

Objetivo: que el agente avise lo importante, no todo.

  • alerts_log para no repetir la misma alerta dos veces.
  • Umbral de materialidad configurable (ej. no avisar variaciones menores a X% salvo pedido explícito).
  • Cruzar frecuencia de alertas con notification_schedules y con "qué tan conversador" pidió ser el usuario.
7
Centro de Control

Panel completo

Objetivo: administrar todo el agente sin tocar la base de datos a mano.

  • Confirmar stack (decisión 09) y autenticación (decisión 10) si no se hizo ya en la Fase 1.
  • Módulos: perfil, personalidad, horarios, noticias, indicadores económicos, mercados seguidos, portafolio, finanzas personales, preferencias de reportes.
  • Asegurar que cada cambio en el panel se refleje de inmediato en lo que usa el agente — misma base de datos, sin caches desincronizados.
8
Cierre

Hardening y uso real

Objetivo: que aguante el uso diario sin sorpresas.

  • Manejo de errores robusto, reintentos, logging/observabilidad de los envíos proactivos.
  • Aislamiento de datos por usuario y manejo seguro de secrets (API keys, tokens).
  • Confirmar decisión de hosting general (decisión 11) según cómo escaló el uso real.
  • Semana de prueba con uso real y ajuste fino de prompts, umbrales de alerta y plantillas de WhatsApp.
05

Riesgos y notas importantes

Aprobación de plantillas Meta: días, no minutos Costo de LLM sube con más proactividad Licencias de datos económicos/noticias — revisar ToS Categorías de gasto: propuesta inicial, no definitiva

El punto de mayor riesgo del spec no es técnico sino de plataforma: si no se resuelve la decisión 07 (mensajería proactiva), buena parte de "el agente debe actuar de forma proactiva" simplemente no es posible tal como está planteado, más allá de qué tan bien esté construido el resto. Por eso el trámite de plantillas arranca en la Fase 0, en paralelo, y no se deja para el final.

06

Antes de tocar código

Elegir, para cada una de las 11 decisiones, si vas con la mejor opción, la económica, o una mezcla — no hace falta decidir todo hoy, pero sí antes de la fase que la necesita.
Iniciar el trámite de WhatsApp Business + plantillas cuanto antes, por el tiempo de aprobación de Meta.
Confirmar el set inicial de categorías de presupuesto propuesto en la Fase 5, o traer tu propia lista.
Dar luz verde a la Fase 0 para arrancar con la base de datos y el orquestador.
